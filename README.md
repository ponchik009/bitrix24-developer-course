## Краткое описание задачи

Необходимо разработать решение для автоматизации кафе-шаурмичной, которое должно включать:
- Учет заказов (ручное создание операторами и возможность создавать данные из внешних систем)
- Учет склада (учет продуктов в разрезе разных филиалов, автоматизация списывания при выполнении заказов и отслеживание остатков)
- Учет клиентов (ведение списка клиентов и их заказов)
- Система уведомлений (оповещение клиентов о статусах заказа)

## Реализованный функционал

Примерный список фич, реализованный в системе:
- В соотвествии с ТЗ настроена структура компании для нескольких филиалов, созданы группы пользователей и воронки
- Для хранения информации используются смарт-процессы:
	- Продукты - содержит справочник продуктов
	- Филиалы - содержит информацию о филиалах (элементы связаны с разделами инфоблока Оргструктура/Подразделения)
	- Остатки продуктов - хранит остатки продуктов в разрезе филиала
	- Меню - содержит список доступных для заказа блюд и цены на них
	- Добавки - хранит продукты, которые могут служить добавками к элементам меню
	- Нормы расходы продуктов на элементы меню - хранит примерный расход продуктов в связке с элементами меню
	- Элементы заказа - хранит элементы меню, добавленные в конкретный заказ. Также хранит стоимость элемента меню на момент заказа
	- Добавки к элементам заказа - хранит добавки, добавленные к конкретным элементам заказа
	- Доступность в филиалах - хранит доступность заказа конкретного пункта меню в разрезе по филиалам
	- Критические остатки - хранит количество продуктов по филиалам, при значении которого будет создаваться задача на дозаказ продуктов
	- Списание продуктов - хранит историю списаний продуктов со склада по филиалам
	- Очередь уведомлений - хранит очередь уведомлений о статусе заказа на отправку клиентам
- Для смарт-процессов настроены права в соответствии с ТЗ или логическим обоснованием
- В сделке добавлены кастомные поля для ведения учета заказов:
	- Поле Сумма заказа, рассчитываемое на основании элементов стоимости заказа и добавок (тип Деньги)
	- Поле Клиент - связка с клиентом
	- Поле Дата и время доставки (Тип Дата со временем)
	- Поле Адрес (Тип Строка)
	- Поле Самовывоз (Тип Логический)
- Создано локальное приложение для интеграции с внешними системами. Общий набор методов:
	- addOrder - создание заказа. Валидируются заполненные поля. Проверяется наличие клиента в базе и создание нового, если клиента по полученным данным не найдено
	- getMenu - получение актуального меню с добавками (например, для отображения в внешних приложениях)
	- getBranches - получение списка филиалов (например, для выбора адреса самовывоза)
	- getClients - получение списка клиентов (с пагинацией)
	- getAvailableMenu - получение доступного меню по филиалу
- В карточке сделки добавлен кастомный таб, реализующий компонент deal.order.items - список элементов заказа с добавками, функциями добавления и удаления
- Настроено автоматическое списывание продуктов со склада филиала при переходе сделки в статус "Готов". Размер списывания определяется на основании расходов продуктов по элементам заказа и добавок
- Реализовано js-расшериние, подключаемое для пользователей с ролью "Шеф-повар". При завершении рабочего дня шеф-повару выводится модальное окно с остатками продуктов по филиалу, записанными в системе, с возможностью актуализировать его реальными значениями
- Реализован агент, сравнивающий остатки филиала с критическими остатками (Смарт-процесс "Критические остатки"), и создающий задачу по дозаказу продуктов. Также есть проверка - если задача с таким же названием у пользователя еще не закрыта, вместо добавления новой задачи происходит обновление существующей
- Реализован обработчик создания элемента в Смарт-процессе "Списание продуктов", измненяющий количество продуктов на складе в соответствии с указанным списанием
- Добавлен компонент contact.orders.list, отображающий историю заказов клиента в карточке на отдельном табе
- Реализована очередь уведомлений, формируемая на определенных стадиях заказа (Готовится, Готов, В доставке, Доставлен) и агент, который отправляет сформированные уведомления на апи-заглушку

## Навигация по проекту

Основной код содержится в папке ```local```. Структура разделов:
- ```/local/components/otus``` - папка компонентов, включающая:
  - ```deal.order.items``` - выводит список элементов заказа, позволяет добавлять и удалять элементы в заказе. Рендерится отдельным табом в сделке
  - ```contact.orders.list``` - выводит историю заказов клиента с использованием компонента ```main.ui.grid```. Рендерится отдельным табом в карточке клиента
  - ```branch.remainder.counter``` - выводит остатки продуктов по филиалу текущего пользователя, позволяет указать фактические остатки. Рендерится в модальном окне при завершении рабочего дня
- ```/local/js/otus``` - папка JS расширений, включающая:
  - ```remainders_calc``` - расширение, подключающееся у пользователей с ролью "Шеф-повар" и отображающее модальное окно сведения остатков при завершении рабочего дня. В модальное окно подгружается компонент ```branch.remainder.counter```
- ```/local/php_interface/src/Otus``` - основная папка проекта, содержащая классы для работы с данными (папка ```Service```), реализацию REST API для локального приложения (папка ```Rest```), код агентов (папка ```Agent```), а также вспомогательные классы

В файле ```/local/php_interface/src/event_handler.php``` содержатся подписки на различные события, включая реализацию многих функций (в будущем требуется рефакторинг и вынесение кода в отдельные классы)

## Технические решения

1. Использование XML_ID

На практике сталкивался с ситуацией, что пользовательские поля в сущностях CRM (или смарт-процессах, или задачах и т.д.) имеют абсолютно нечитаемый код поля. При этом поле может использоваться давно и содержать в себе много данных, что сильно усложняет попытку пересоздать поле с читабильным кодом. К тому же, без использования миграций код такого поля на тестовой/релизной/любой-другой площадке будет отличаться.

В определенный момент я решил полностью отказаться от кода поля и перейти на XML_ID, которым можно управлять только в админ-панели и который можно определить не только для пользовательского поля, но и для Смарт-процесса, элемента списка (у полей типа Список). На практике код получается сильно раздутым, но повышается читабельность.

Как итог, XML_ID позволяет полностью отказаться от различных нечитабельных значений вроде кода поля у Пользовательских полей или идентификатора типа сущности у Смарт-процессов.

2. AJAX запросы только внутри компонентов

Не знаю, насколько bitrix-way реализовывать ajax запросы только внутри компонентов, но мне это показалось очень удобной и лаконичной фичей, т.к. пре/постпроверки можно подключать "из коробки", а все нужные методы компонуются в едином классе. Планирую попробовать использовать этот подход в проектах на БУС, реализуя шаблон с помощью фронтовых фреймворков (React) и используя компонент только как контроллер для отдачи данных.

3. Класс ```/local/php_interface/src/Otus/Container/CRMFactoryContainer.php``` - контейнер фабрик

Использовать идентификатор типа, который при ручном переносе на другую площадку может поменяться, казалось мне плохой идеей еще при первом знакомстве с Битрикс24. Такая ситуация, встречающаяся в битриксе повсеместно, уже не раз заставляла меня страдать, так что по возможности я стараюсь полностью отказываться от любого вида ID-шников или прочих констант, которыми нельзя управлять и которые могут поменяться в другой базе.

## Развитие проекта

1. Рефакторинг

Очевидно, что многие куски кода лежат не там, где нужно (особенно в файле ```event_handler```). Нужно разлложить все по полкам, чтобы получить более читабельную версию проекта

2. Внедрение DI и Autowiring

Концепция, которая на мой взгляд вполне реализуема в Битриксе. Сейчас мои сервисы сами определяют свои зависимости, что не очень хорошо с точки зрения проектирования. Если когда-нибудь я попробую внедрить тесты в такой код, то столкнусь с большими проблемами создания моков.

Для решения проблемы необходимо вынести все зависимости классов в конструктор, передавая их "сверху" (паттерн Dependency Injection). А чтобы не создавать кучу инстансов руками, необходимо почитать гайды про Autowiring и Reflection API (скорее всего для фабрик потребуется отдельный Декоратор, потому что они создаются не через конструктор).

3. Внедрение тестов

Использование паттерна DI должно сделать код более расположенным к тестированию - мы сможем без особых проблем мокать зависимости и передавать их через конструктор. 

Предугадываю, что для тестирования Сервисов как вероятных точек отказа не хватит простых моков - нужно будет поднимать базу и писать интеграционные тесты. Это слабо изученный с моей стороны вопрос, но предполагаю, что без миграций не обойтись. Условный алгоритм будет включать в себя поднятие базы (например, в Docker), накатывание миграций для повторения структуры созданных сущностей, а также наполнение базы предопределенными данными для тестирования.
